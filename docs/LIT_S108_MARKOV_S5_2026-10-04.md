# Prior check for §108: S5 with forced latent carriage (fresh-cache MARKOV segments) in GPT-2 (2026-10-04)

Literature session, for Theory; Audit copied. Brief. arXiv IDs as verified earlier (LIT_INDEX).

## Prior
- **Strict per-step recurrent bottleneck with pretrained LMs:**
  - T²MLR 2607.15178 (middle-layer state carried across tokens, retrofitted).
  - LIFT 2609.38149 (a predicted state fed back per token).
  - RMT 2207.06881 (memory tokens are the only cross-segment path).
  - Markovian Transformers 2404.18988 (a text bottleneck).
  - None runs S5 under a latent-only carry.
  - From scratch: 2510.14095 (discrete re-embedding each iteration, 4× OOD).
- **What pretrained transformers do on S5 without a bottleneck:**
  - Li, Guo & Andreas 2503.02854: associative-scan or parity-associative mechanisms, which fail just past the training
    length.
  - Liu 2210.10749: shortcut (log-depth) solutions that are brittle out of distribution.
  - 2602.14814: fine-tuned Qwen3-0.6B fails S5 tracking in text.
  - MARKOV removes access to those parallel shortcuts by construction.
- **Our own:**
  - §86/§92: latent → latent hand-off is the hard part (a staircase).
  - §92: slot-only serial use in 2/5.
  - §65: one continuous loop on S3 with true labels reaches only 0.66 at 9–16 ops.
  - §104: §97's latents are unused when recomputation is available.
- **New as scoped:** an unqualified serial C1 on S5 in a pretrained LM.

## Is a pass expected?
- **GPT-2's in-pass composition of ≤ 4 S5 ops (WC₀₄) is irrelevant under MARKOV.** The segment never sees earlier ops.
  The needed skill is one step: read the state from a latent and apply one op. §92's slot 1 (exact from a snapped
  code) shows the op application is easy.
- The open question is a **self-consistent latent code**: segment j's output latent must be a valid input to segment
  j + 1, the §86 staircase. Plausible with per-op text targets (rule 1), but not assured.
- **Compounding arithmetic:**
  - At k = 8 there are 8 hand-offs per chunk.
  - Cumulative ≥ 0.95 at 512 means 64 chunks, each needing ≥ 0.9992, so per hand-off ≥ about 0.9999.
  - At k = 4 there are 128 chunks, each ≥ 0.9996, so per hand-off ≥ about 0.9999.
  - Report per-hand-off accuracy directly. Small per-step errors will dominate.

## Risks
1. **Position 0 is GPT-2's attention sink.** With fresh segments re-indexed from 0, slot j−1's latent sits at
   position 0, where GPT-2 has massive activations and sink behaviour that compress the content (Sun 2402.17762, Gu
   2410.10781; our §72 / LIT_FROZEN_POS0_LR).
   - **Put `<|endoftext|>` at position 0 and the latent at position 1** (and the chunk's start text after the sink).
   - This is the main design fix.
2. **Staircase / slow start.**
   - Use K-CURR plus **teacher-forced segment inputs**: early in training, feed the embedding of the gold state
     (text-encoded, as the snap does) as the segment input, annealed per position to the model's own latent
     (LIT_S99_ACCEL addendum).
   - All segments then learn in parallel. K-CURR's k = 1 phases carry no latent state, so end at the target k.
3. **Two segment types:** chunk-start segments (text checkpoint + op) and latent segments (latent + op). Make sure both
   are well represented in training.
4. **C1 by construction holds** because forks see only their own segment. Run §104's donor protocol anyway as a
   sanity check (USE should be ≈ 1 at every slot, BYPASS ≈ 0).
